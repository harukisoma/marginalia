# 同期障害の復旧（2026-11-23）

## 原因とクラウド側の修正

`save_notebook` は世代番号の競合を SQLSTATE `40001` として返していた。PostgREST 14.18 ではこのコードが同じトランザクションの無限再試行を起こし、CPUの高負荷と `PGRST002` / HTTP 503 に波及した。ブラウザの12秒タイムアウトには、この503をSDKが再試行した後の打ち切りも含まれていた。

Supabaseの公式な対処方法:
https://supabase.com/kb/troubleshooting/high-cpu-and-infinite-transaction-retries-when-using-custom-error-codes-in-rpc-functions-77326b

`supabase/migrations/20261123_safe_sync_conflicts.sql` は、クラウドの全ノートと修正前の関数定義を非公開スキーマ `marginalia_recovery` にコピーした後、関数の競合コードだけを `PT409` に変更する。権限・所有者・保存先・ID・既存のレコードは変更しない。保護テーブルはRLSを有効にし、public/anon/authenticatedの権限を明示的に取り消す。

本番で修正済みの場合も、スクリプトは保護コピーを上書きせず実行できる。想定と違う関数定義なら処理を止める。

既存のループが残る場合は、ログのprocess_idと `pg_stat_activity` を照合し、該当する保存処理だけを終了する。今回の適用後の確認ではループ中の保存処理は残っておらず、追加の接続終了やプロジェクト再起動は不要だった。

## アプリ側の再発防止

- `PT409` と旧サーバーの `40001` を、最新状態を読み直してから統合する競合として扱う。短いランダム待機を挟み、最大8回。その後も間隔を空けて再試行する。
- SDK内の不透明なデータAPI再試行を無効化し、アプリの再試行に統一。5秒から最大120秒へ間隔を広げ、障害中に定期処理が再試行を増やさない。
- セッション取得と通信全体に上限を設け、応答しない通信処理が同期の実行枠を保持し続けるのを防ぐ。データ送受信は45秒まで待てる。
- エラーは日本語で、端末の記録を保持していること・自動再接続することを表示。「今すぐ同期」は待機時間を待たず試せる。
- 切断、タイムアウト、保存後の応答消失でも、次の試行は必ずサーバーを読み直してから統合する。無条件上書きや空のノート送信はしない。

Yjs、IndexedDB、バックアップv1、同期アカウントの関連付け、既存の削除防止・事前保護コピーは維持している。ログアウト、キャッシュ削除、端末データの初期化は復旧方法に含めない。

## 検証

`npm test`、`npm run build`、`PAGES_BUILD=1 npm run build`、秘密検出を実行する。

合成データで、409の同時編集・両端末の未同期ノート・障害中のバックオフ・手動復旧・保存応答の消失・通信中の追加編集・認証待機中の中止を確認する。既存のアカウント混在防止、旧形式のバックアップ、削除防止の検証も継続する。

本番の確認は保存関数への合成所有者での非書き込み競合チェック、読み取り専用メタデータ取得、本人が承認した通常の同期操作だけを使う。本人の本文をテスト用に書き換えない。
